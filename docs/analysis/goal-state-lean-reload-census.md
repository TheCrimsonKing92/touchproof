# Conductor tick history and Timeline readers

The conduct loop reloads its selected goals in the sweep and rebuilds the tracked goals before dispatch refresh, terminal sweep and the rest of the tick. The census covers reads during that rebuild, policy decisions and worker preparation, completion and persistence. It includes conditional paths such as operator intents and provider recovery. Calls that open a separate store read are identified where they matter to a lean reload. [Tick entry](../../src/Mcg.AgentOrchestrator.App/Cli/CliCommandHandlers.Goals.cs#L1518) · [Kernel refresh](../../src/Mcg.AgentOrchestrator.App/Cli/CliCommandHandlers.Goals.cs#L1943)

A writer that changes a goal document, task history or Timeline rows must advance the goal row version in the same transaction. The loop treats equal versions as equal content. Changed goals explicitly requested from the archive use the same lean projection as hot goals, and their deferred accessors resolve the archive document when needed. Archive stubbing and recompression preserve the content. An out-of-band write that leaves the version unchanged can stay invisible until the row version changes or the loop restarts.

The reuse-aware tick reload projects the current records and counts. It leaves the cached Timeline and task history collections empty. In the tables, “Moved” means the domain Timeline or task history getter now supplies persisted rows through `GoalTimelineStore.ReadAsync` or `GoalTaskHistoryStore.ReadAsync` on demand. Timeline reads include staged appends. Task history is restored before any mutation that reads or changes the retained lists, so later consumers see that mutation. “Not needed” means the caller uses a projection or owns a separate full load.

Tick baseline capture, tracked-goal refresh and checkpoint construction carry the transient completeness data between kernels and into SQLite. Full exports used by evidence readers still materialize their histories through the getters. Scheduling and other readers that still need retired events may load them later in the same tick.

## Tick snapshot byte coverage

The receipt totals describe the logical UTF-8 representation passed to or produced by repository serializers, including JSON whitespace and escapes. Every invocation contributes independently, including repeated materializations and retries. SQLite allocation, compressed size, parameters, columns, and separate task-history, timeline and human-input rows are outside the snapshot payload.

| Repository boundary | Byte coverage |
| --- | --- |
| Full, targeted or lean hot reload, deferred timeline or history access, lazy terminal metadata, creation dependency scans, attention fallback and archive maintenance parsing of hot rows | **Unknown** for each full TEXT parse, including a metadata stub. Its string length gives a UTF-16 character count. |
| Compressed archive hydration and deferred projections, including timeline and history marker passes and attention fallbacks | **Exact** for each parser receiving the decoded document. The existing Brotli decode exposes the uncompressed UTF-8 length. Legacy archive TEXT is **unknown** on the string path. |
| Backlog similarity, provider evidence and usage stream projections, including diagnostic replays | **Exact** for a complete decoded frame or fully read memory stream. An incomplete stream or a stream with no available logical length is **unknown**. A replay that reconstructs a string through a text reader is **unknown** because the reader can normalize the byte representation. |
| Projected snapshot serialization during upsert | **Exact** for a changed row whose existing write path computes the UTF-8 count. Serializer work survives later rollback. If serialization ran and a failure or unchanged row prevented that count, the write is **unknown**. |
| Full goal serialization for creation or checkpoint comparisons, projected snapshots for conflict-merge diagnostics, and archive stub serialization | **Unknown** because the existing string and JSON element serializers expose no byte count. |
| Metadata-column or indexed reads, SQLite-side field extraction, version-matched snapshot reuse, row-only access, archive recompression and failures before serializer entry | **Zero** goal snapshot serializer bytes. Deferred access to a cached snapshot can still invoke a separate full parse when used. |

The receipt seals each direction independently after the tick's checkpoints. In-flight snapshot work makes its possible directions unknown at that point. The initiating tick owns scheduled retention, state-log checking and board filing work. On paths that deliver the receipt before the workspace activation sweep, the read total is unknown because the sweep may load worker-usage snapshots. A later completion cannot amend the receipt or contribute to another tick. Idle polling and shutdown work outside completed ticks, independent CLI and worker operations, and jobs outside the tick's invocation scope are outside the totals. Observation-only ticks emit the counter line through their existing log path.
